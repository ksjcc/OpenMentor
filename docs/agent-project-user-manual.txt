AgentCareer 项目精华技术文档
版本：基于当前仓库整理
整理日期：2026-06-01

一、项目本质定位

AgentCareer 不是一个普通的 AI 问答系统，也不是简单的“简历解析 + 模拟面试”组合，而是一套面向技术求职场景的个性化 AI 面试与成长闭环系统。

它解决的核心问题有三类：
1. 如何让 AI 面试不是固定问答，而是能够根据用户回答质量、历史弱点和当前上下文动态追问
2. 如何让系统真正具备“长期认识用户”的能力，而不是每轮对话都从零开始
3. 如何把一次面试结果沉淀为可复用的成长资产，持续服务后续学习、复盘与推荐

因此，这个项目的真正亮点不在于“接了大模型”，而在于把以下能力串成了一个完整系统：
- 画像建模
- 多 Agent 协调决策
- 检索规划
- 混合检索
- GraphRAG
- 记忆分层
- 异步后处理
- 学习闭环
- 可观测运行时


二、项目最核心的系统闭环

整个项目围绕一条完整成长链路展开：

1. 面试前
- 解析简历与项目经历
- 生成结构化职业画像
- 建立长期偏好与能力基础

2. 面试中
- 生成首题
- 对用户回答进行评分
- 判断是否需要检索
- 动态选择记忆层和检索策略
- 综合多个 Agent 的建议形成最终动作
- 生成追问、下一题或更高难度问题

3. 面试后
- 提炼优势、弱项、知识点、闪卡、总结
- 合并更新画像
- 写入长期记忆
- 构建知识图谱与 GraphRAG 索引
- 生成学习推荐与复习计划

4. 平时学习阶段
- 基于个人历史面试和知识结构做问答
- 基于闪卡执行复习
- 基于 Dashboard 观察能力变化

这个闭环意味着系统不只是在“回答问题”，而是在持续构建用户的成长模型。


三、项目精华一：多 Agent 协调决策，而不是单模型直出

1. 核心思想

项目没有把“下一步做什么”交给单次 Prompt 直接决定，而是拆成多个职责明确的 Agent 和决策模块协同完成。

核心角色包括：
- `TechInterviewerAgent`：负责出题与下一题生成
- `FollowUpAgent`：负责追问生成
- `ScoreAgent`：负责对用户回答进行评分与弱项识别
- `KnowledgeExtractorAgent`：负责面试结束后的结构化提炼
- `ReviewPlannerAgent`：负责学习计划生成
- `ResumeProfileAgent`：负责从简历和项目文本中抽取职业画像
- `DriftQuestionAgent`：服务于图谱漂移搜索与扩展问题生成

2. 决策不是单点判断，而是多信号融合

在实时面试阶段，系统会同时引入多类判断信号：
- 评分信号：回答质量如何，是否答偏，弱项是什么
- 难度信号：是否应该加深问题、提高难度
- 记忆信号：用户历史薄弱点是否值得继续追问
- 图谱信号：当前问题是否适合做关联扩展或多跳推理

这些信号分别来自：
- `DifficultyPolicy`
- `MemoryDecisionService`
- `GraphDecisionService`
- `ScoreAgent`

最终由 `DecisionAggregator` 聚合为统一动作。

3. 聚合决策机制的价值

系统最终动作不是单一模型临时拍板，而是多个模块协商后的结果，支持的动作包括：
- `FOLLOW_UP`
- `HARDER`
- `NEXT`
- `FINISH`

实现效果：
- 追问行为更稳定，不容易因为某一次模型波动直接偏题
- 系统能兼顾“当前回答质量”和“长期成长价值”
- 面试节奏更接近真实面试官，而不是模板式追问

4. 并行决策能力

项目中对部分决策过程采用并行化处理，例如记忆决策与图谱决策可以并行执行，再统一汇总。

实现效果：
- 降低实时面试阶段的等待时间
- 在不牺牲决策维度的前提下控制整体延迟


四、项目精华二：Orchestrator 编排式运行时

1. 核心思想

项目将一次面试回答处理拆成一个可编排、可恢复、可观测的实时流水线，而不是把所有逻辑写成串行调用。

核心编排入口是：
- `AgentOrchestrator`

核心阶段包括：
- `SCORING`
- `RETRIEVAL_PLANNING`
- `GRAPH_RAG_ENRICHMENT`
- `DECISIONING`
- `AGGREGATION`
- `PROMPT_ASSEMBLY`
- `GENERATION`

2. 每个阶段职责明确

- `SCORING`
  负责评分、识别弱项、提取后续决策信号

- `RETRIEVAL_PLANNING`
  负责决定是否检索、检索什么、优先走哪类检索器、使用哪一层记忆

- `GRAPH_RAG_ENRICHMENT`
  负责补充图谱与检索增强上下文

- `DECISIONING`
  负责汇总多个模块建议

- `AGGREGATION`
  负责形成唯一最终动作

- `PROMPT_ASSEMBLY`
  负责把画像、记忆、上下文、图谱信息组织为当前生成输入

- `GENERATION`
  负责真正生成追问、下一题或结束提示

3. 编排运行时的价值

相比普通调用链，这种设计带来了四个明显优势：
- 流程可观测：每阶段都能统计耗时和状态
- 流程可恢复：某一阶段异常时不一定整条链路失败
- 流程可降级：可以用 fallback 方案兜底继续运行
- 流程可优化：后续可以针对某一阶段单独调优

4. 阶段恢复与降级机制

项目中每个关键阶段都配置了恢复策略，例如：
- 评分失败时使用空评分结果兜底
- 检索规划失败时退化到保守检索计划
- 图谱增强失败时跳过 GraphRAG 继续执行
- 聚合失败时退化为 `NEXT`
- Prompt 组装失败时使用简化上下文
- 最终生成失败时返回安全兜底话术

实现效果：
- 提升真实运行时的韧性
- 避免某个 AI 子模块抖动导致整轮面试直接中断


五、项目精华三：检索前先做 Planning，而不是默认全量 RAG

1. 核心思想

项目不是“每个问题都无脑检索”，而是在检索前先做一次检索规划。

相关核心模块：
- `RetrievalPlanningService`
- `RetrievalSlottingService`

2. 检索规划关注的不是实现，而是问题属性

系统先判断：
- 当前问题属于什么意图
- 当前问题复杂度如何
- 是否依赖历史上下文
- 是否需要历史记忆
- 是否需要技术知识召回
- 是否需要图谱多跳推理

规划信号包括：
- `intent`
- `complexity`
- `contextDependent`
- `needsHistoricalContext`
- `needsConceptRetrieval`
- `needsGraphReasoning`

3. 检索槽位机制

系统会先把当前输入分成三类检索槽位：
- `NO_RAG`
  适用于寒暄、控制指令、无需知识补充的输入

- `LIGHT_RAG`
  适用于超短输入或轻量上下文补充场景

- `FULL_RAG`
  适用于技术性、上下文性、知识性较强的问题

实现效果：
- 避免所有输入都触发重检索
- 控制延迟和成本
- 让系统对不同交互强度有更细致的响应策略

4. 检索规划输出的关键内容

系统最终会输出结构化检索计划，包括：
- 主检索器类型
- 是否需要 Memory
- 是否需要 Vector
- 是否需要 Graph
- 是否需要 HyDE
- 是否启用关键词补偿
- GraphRAG 模式
- TopK
- 检索预算

实现效果：
- 检索从“固定策略”升级为“按场景自适应策略”


六、项目精华四：三层记忆分工 + 多存储协同

1. 记忆不是一层，而是三层职责分工

项目中明确设计了三层记忆路由：
- `SESSION`
- `GROWTH`
- `PREFERENCE`

其含义分别是：

- `SESSION`
  面向当前会话的短期上下文记忆，主要服务当前轮对话连续性和追问承接

- `GROWTH`
  面向长期成长的历史记忆，主要沉淀用户的弱项、总结、历史表现和复习轨迹

- `PREFERENCE`
  面向稳定用户画像和个人偏好的记忆，主要反映目标岗位、技术栈、学习偏好、简历背景等长期稳定信息

2. 三层记忆不是手工指定，而是动态路由

核心模块：
- `MemoryLayerRouterService`

系统会根据问题类型与语义自动决定：
- 主记忆层用哪一层
- 备用记忆层用哪一层

例如：
- 当前轮追问、继续刚才问题这类输入优先走 `SESSION`
- 岗位方向、偏好、技术栈、简历这类输入优先走 `PREFERENCE`
- 历史薄弱点、成长轨迹、复习记录这类输入优先走 `GROWTH`

实现效果：
- 记忆调用更贴近真实语义，而不是一刀切检索全部历史
- 降低无关信息干扰，提升召回质量

3. 三层记忆底层映射到多种存储

项目中底层定义了多种记忆存储类型：
- `REDIS_SESSION_CACHE`
- `MEMORY_SUMMARY_MD`
- `MEMORY_CHUNK`
- `PGVECTOR`
- `INTERVIEW_HISTORY`
- `MEMORY_PROFILE_JSON`
- `USER_PROFILE`

按职责可浓缩为四类核心存储形态：

- 短期缓存存储
  代表：`REDIS_SESSION_CACHE`
  作用：保存最近多轮对话，支撑实时连续追问

- 长期文本摘要存储
  代表：`MEMORY_SUMMARY_MD`、`INTERVIEW_HISTORY`
  作用：沉淀结构化总结与历史面试文本

- 长期语义片段与向量存储
  代表：`MEMORY_CHUNK`、`PGVECTOR`
  作用：支持语义召回、相似问题检索和 RAG 增强

- 稳定画像存储
  代表：`MEMORY_PROFILE_JSON`、`USER_PROFILE`
  作用：保存用户长期稳定画像和偏好配置

这就是项目可以概括为的：
- 三层记忆分工
- 四层存储承载

4. 这种设计的价值

相比把所有历史信息都塞进一个库里，这种方式更有工程价值：
- 短期上下文和长期成长信息不会混淆
- 结构化画像和自由文本记忆可以分别服务不同场景
- 既支持精确画像读取，也支持语义相似召回
- 为后续做记忆压缩、记忆污染控制和个性化推荐打下基础


七、项目精华五：混合检索不是单一路径，而是 Memory / Vector / Graph 协同

1. 核心思想

项目没有将检索能力限制在单一向量库，而是建立了混合检索体系。

核心模块：
- `HybridRetriever`
- `MemoryRetriever`
- `GraphRagRetriever`
- `RerankService`
- `HydeQueryExpansionService`

2. 检索源协同

系统可组合使用的检索能力包括：
- 基于会话与历史记录的 Memory 检索
- 基于向量语义的 Vector 检索
- 基于知识关系与多跳结构的 GraphRAG 检索
- 基于关键词的 fallback 检索

3. 辅助增强能力

除了直接召回，项目还加入了：
- HyDE 查询扩展：先扩展意图再检索
- Rerank 重排序：对多源结果二次排序
- 去重合并：避免多检索器重复输出

实现效果：
- 提升召回覆盖度
- 改善复杂问题下的上下文质量
- 降低单一检索器导致的信息盲区

4. 为什么这是亮点

普通项目常见做法是“一个向量库 + 一个 topK”，而这个项目已经具备：
- 检索前规划
- 检索中路由
- 检索后重排
- 检索预算控制

这说明检索系统已经具备接近运行时能力，而不是简单工具调用。


八、项目精华六：GraphRAG 不是装饰，而是独立的增强子系统

1. 核心思想

项目中的图谱能力不是只做可视化展示，而是真正参与检索增强和问题理解。

相关模块包括：
- `GraphRagRetriever`
- `GraphRagQueryClassifier`
- `GraphRagRetrievalRouter`
- `GraphRagSearchGuard`
- `GraphRagIndexerService`
- `GraphCommunityService`
- `CommunityReportAgent`

2. GraphRAG 支持多模式

项目支持的模式包括：
- `LOCAL`
- `GLOBAL`
- `DRIFT`
- `VECTOR`
- `MEMORY`
- `AUTO`

含义可以概括为：
- `LOCAL`：局部知识点邻域检索
- `GLOBAL`：全局知识结构与综合主题检索
- `DRIFT`：围绕当前主题做扩展、迁移与发散性搜索
- `VECTOR`：向量优先模式
- `MEMORY`：记忆优先模式
- `AUTO`：由分类器自动选择

3. 图谱不只服务查询，也服务索引与结构沉淀

项目会在面试后对信息进行：
- 实体抽取
- 关系抽取
- 实体合并/更新
- 社区构建
- 社区报告生成

实现效果：
- 用户知识结构不只是文本堆积，而是形成关系网络
- 后续问题生成、知识问答、学习推荐都可以利用图结构信号

4. GraphRAG 的真实价值

它特别适合处理：
- 多知识点关联问题
- 系统设计类问题
- 弱项周边扩展学习
- 当前问题与历史知识结构的联动


九、项目精华七：Retrieval Budget + Search Guard，体现了运行时治理意识

1. 核心思想

项目不是无限制调用检索和大模型，而是为检索过程引入预算与守卫机制。

核心模块：
- `RetrievalBudget`
- `RetrievalBudgetService`
- `GraphRagSearchGuard`

2. 受控的资源项

预算控制的对象包括：
- retriever 调用次数
- graph hop 次数
- chunk 使用量
- LLM 调用次数
- search step 次数
- timeout

3. 守卫机制的行为

搜索守卫会做这些事情：
- 超过预算即停止
- 搜索步数耗尽即停止
- 同一检索器 + 同一查询去重
- 防止重复搜索

实现效果：
- 控制复杂检索导致的尾延迟
- 降低实时面试场景中资源失控风险
- 使 GraphRAG 可以真正用于在线实时链路


十、项目精华八：Prompt 不只是拼接，而是有预算分配和压缩策略

1. 核心思想

项目没有把画像、上下文、图谱、记忆全部无差别塞入 Prompt，而是做了动作感知的上下文压缩与预算分配。

核心模块：
- `PromptBuilder`
- `PromptContext`
- `PromptBudgetAllocator`
- `DefaultPromptBudgetAllocator`

2. Prompt 压缩是按任务类型区分的

不同动作下，系统会给不同上下文分配不同预算，例如：
- `FOLLOW_UP`
  更关注 recent context、弱项记忆、图谱推理和当前题连续性

- `NEXT` / `HARDER` / `NEW_QUESTION`
  更关注知识背景、画像、总结、检索结果

- `SCORE`
  更关注当前回答与少量必要背景

- `EXTRACTION`
  更关注完整对话内容

- `PROFILE`
  更关注简历与目标岗位

3. 上下文压缩不是简单截断，而是有明确的压缩对象

项目压缩的重点对象包括：
- 最近对话上下文 `recentContext`
- 检索召回记忆 `ragMemories`
- 长期总结 `summaryMd`
- 结构化画像 `profileJson`
- 图谱推理结果 `graphReasoning`
- 简历文本 `resumeText`
- 项目摘要 `projectSummary`

这说明系统并不是简单把一大段历史对话直接拼进去，而是先把不同来源的上下文拆开，再按任务重新分配篇幅。

4. 上下文压缩与实时链路是联动的

在 `PromptAssemblyStage` 中，系统会先统一组装：
- 当前问题
- 当前回答
- 最近会话上下文
- 检索上下文
- 画像信息
- 历史总结
- 图谱推理信号

然后再通过 `PromptBudgetAllocator` 按动作类型做二次压缩。

实现效果：
- 实时追问时优先保留当前轮连续性
- 下一题生成时优先保留知识背景和成长信息
- 评分与提炼任务不会被无关长上下文污染
- 长对话场景下仍能控制 Prompt 长度和稳定性

5. 这种设计的价值

实现效果：
- 控制 Prompt 长度
- 减少无关上下文污染
- 提高生成稳定性
- 让不同 Agent 看到更适合自己任务的信息


十一、项目精华九：异步后处理把“实时面试”和“成长沉淀”拆开

1. 核心思想

系统将“用户正在交互的主链路”和“面试结束后的重处理链路”分开。

核心技术：
- RabbitMQ
- 生产者/消费者模式
- 后处理状态字段
- 重试计数与错误记录

2. 后处理包含的关键能力

面试结束后，系统会异步执行：
- 知识提炼结果解析
- 用户画像合并
- 长期记忆更新
- 闪卡生成
- 图谱索引更新
- 社区重建与报告生成

3. 这种拆分的价值

实现效果：
- 用户结束面试时不必等待所有沉淀动作完成
- 重操作与实时响应解耦
- 系统更容易扩展更复杂的面后分析能力


十二、项目精华十：从“对话结果”沉淀为“成长资产”

1. 画像沉淀
- 用户画像不是一次性生成，而是可以随着面试结果持续修正

2. 记忆沉淀
- 面试结果会写入长期记忆，而不是只存在历史消息里

3. 图谱沉淀
- 知识点和关系会形成结构网络

4. 闪卡沉淀
- 重要知识点会转为可复习卡片

5. 学习计划沉淀
- 系统会基于弱项和岗位目标输出后续行动建议

这个设计说明项目真正关心的是：
- 如何把面试行为转成长期可积累、可检索、可复习、可推荐的数据资产


十二点五、项目补充精华：长期记忆不是概念，而是“结构化沉淀 + 文本摘要 + 语义片段 + 向量索引”的组合实现

1. 长期记忆的真实落地路径

项目中的长期记忆不是抽象口号，而是已经拆成多种可落库、可检索、可追溯的形态：
- `memory_profile_json`
  保存画像类 JSON 版本，适合表达用户长期稳定身份信息

- `memory_summary_md`
  保存 Markdown 总结，适合表达整体成长摘要、面试提炼摘要

- `memory_chunk`
  保存片段化文本记忆，适合表达可检索的细粒度知识和面试结论

- `pgvector`
  保存 `memory_chunk` 对应的向量索引，支持语义召回

2. 长期记忆的写入机制

长期记忆主要通过 `MemoryService` 完成更新，关键写入动作包括：
- 画像初始化后写入 `profileJson`
- 面试提炼结果写入 `summaryMd`
- 面试中的关键信息切成 chunk 写入 `memoryChunk`
- chunk 在写入 MySQL 后进一步写入向量库

实现效果：
- 同一份成长信息同时具备“结构化可读”和“语义可检索”两种能力
- 既支持版本化追溯，也支持后续 RAG 召回

3. 长期记忆的容错设计

项目对长期记忆写入做了明显的工程化处理：
- MySQL 文本记忆先落库
- 向量库写入失败时不阻塞主流程
- 即使 pgvector 暂时异常，文本长期记忆仍然保留

实现效果：
- 长期记忆沉淀具备降级能力
- 系统不会因为向量链路异常而丢失核心成长数据

4. 长期记忆的读取不是单一路径

在实时检索中，系统会根据记忆层和检索计划动态选择长期记忆来源，例如：
- 从 `memory_summary_md` 读取整体总结和提炼总结
- 从 `memory_chunk` 读取细粒度历史片段
- 从 `pgvector` 读取语义相似内容
- 从 `interview_history` 读取最近历史面试 transcript 和 summary

这意味着长期记忆不只是“存起来”，而是已经具备真正的在线可用性。


十三、项目精华十一：Dashboard 不是展示页，而是成长结果的聚合层

1. 聚合内容

Dashboard 汇总的不是简单统计，而是成长结果：
- 技能雷达
- 最近面试
- 今日待复习数
- 薄弱点排行
- AI 学习建议
- 学习推荐与计划

2. 背后的技术点

- 多表聚合
- 能力图映射
- 弱项权重汇总
- 画像 + 历史面试联合分析
- 闪卡复习状态统计

实现效果：
- 把后台复杂能力最终转化为用户可感知的成长视图
- 让整个系统不止能“生成内容”，还能“表达成长结果”


十四、项目精华十二：Trace 与阶段指标让系统具备可观测性

1. 核心思想

项目中已经引入了阶段级 Trace 机制，而不是只在控制台打印日志。

核心模块：
- `TraceContext`
- `TraceEvent`
- `TracePersistenceService`
- `TraceAnalyticsService`
- `PipelineRuntime`
- `PipelineStageExecutor`

2. 可观测的内容

系统能够记录：
- 每个阶段开始和结束时间
- 阶段耗时
- 输入输出摘要
- 恢复动作
- fallback 情况
- 使用的 graph mode
- prompt 长度
- 输出长度

3. 这种设计的价值

实现效果：
- 可以分析慢阶段在哪里
- 可以分析哪些阶段经常 fallback
- 可以为后续性能治理和质量调优提供数据基础

这也是项目从 Demo 走向工程系统的重要标志。


十五、项目精华十三：工程化稳定性设计

项目已经具备多项真实系统才会关心的稳定性设计：

1. 缓存与数据库职责分离
- 先写 MySQL，事务成功后再更新 Redis，避免脏缓存

2. 限流保护
- 对 AI 高频调用进行用户级时间窗口限流

3. 全局异常处理
- 统一业务异常与系统异常出口

4. 安全 Guard
- 对 AI 调用和生成过程设置保护边界

5. Fallback 思维
- 评分、检索、图谱、聚合、Prompt、生成多个阶段都具备兜底路径

6. 异步状态可追踪
- 后处理任务具备状态字段、错误字段、重试字段

这些能力的意义在于：
- 项目不只是“能跑通”
- 更开始关注“在不稳定环境下还能不能继续稳定运行”

十七、这个项目最值得强调的技术价值

如果要用最浓缩的方式概括，这个项目的精华可以总结为七点：

1. 它把技术面试做成了一个多阶段实时决策系统，而不是固定模板问答
2. 它把记忆做成了三层职责分工，并落到了多存储协同上
3. 它把检索做成了 Planning + Slotting + Hybrid Retrieval + Rerank 的组合体系
4. 它把 GraphRAG 做成了真正参与在线链路的增强子系统
5. 它把面试结束后的提炼、画像、图谱、闪卡和推荐串成了成长闭环
6. 它具备 Budget、Guard、Fallback、Trace、Async 的运行时治理意识
7. 它最终输出的不是单次回答，而是长期成长资产和可视化成长结果


十七点五、项目补充精华：GraphRAG 检索已经形成“分类 -> 规划 -> 路由 -> 多策略执行 -> 守卫 -> 重排”的完整链路

1. GraphRAG 检索不是单点调用

项目中的 GraphRAG 检索链路已经拆分为多个环节：
- `GraphRagQueryClassifier`
  负责判断当前查询更适合哪类图检索模式

- `GraphRagRetriever`
  负责基于计划执行多检索器组合

- `GraphRagRetrievalRouter`
  负责把不同检索类型路由到具体策略

- `GraphRagSearchGuard`
  负责预算、去重和停止条件控制

- `RerankService`
  负责对多源图检索结果进行重排

2. GraphRAG 分类不是写死模式，而是按问题类型自适应

分类时会考虑的问题特征包括：
- 是否是全局总结型问题
- 是否是多跳推理型问题
- 是否是明确知识点局部问题
- 是否是跨主题问题
- 是否处于实时场景

最终形成的典型模式包括：
- `GLOBAL`
  适合全局总结、成长报告、体系化问题

- `LOCAL`
  适合围绕明确知识点和局部实体做邻域检索

- `DRIFT`
  适合跨主题、多跳、扩展型问题

3. 不同 GraphRAG 策略各自承担不同职责

- `Local Search`
  从实体、关系、来源片段出发，补充局部知识结构，并结合向量召回补充邻域上下文

- `Global Search`
  以社区报告为全局上下文来源，适合总结类和全局判断类问题

- `Drift Search`
  先取全局社区报告，再借助 `DriftQuestionAgent` 生成细化查询，再把这些查询交给 Local Search 扩展

这说明 GraphRAG 在项目里不是简单“查图”，而是带有推理路径设计的多策略系统。

4. GraphRAG 与实时系统协同的关键点

项目已经考虑到在线使用 GraphRAG 的现实问题：
- 实时问题和分析问题可走不同预算
- 每类检索器都受预算和守卫控制
- 结果会做去重、合并和 rerank
- 超预算、超时或步数耗尽会及时停止

实现效果：
- GraphRAG 不只是离线分析组件
- 已经可以受控地参与实时面试问答链路


十八、总结

AgentCareer 最有价值的地方，不是它“用了多少 AI 名词”，而是它已经形成了一套比较完整的项目方法论：

1. 用画像建立个性化起点
2. 用多 Agent 和编排机制提升面试过程质量
3. 用三层记忆与混合检索提升上下文利用效率
4. 用 GraphRAG 处理复杂知识关系
5. 用异步后处理把面试结果沉淀为长期资产
6. 用 Dashboard、闪卡和学习计划把能力落到成长闭环
7. 用 Trace、Budget、Guard、Fallback 提升系统可运行性

因此，这个项目可以被准确概括为：

一套面向技术求职场景的、具备多 Agent 协调决策、三层记忆分工、混合检索增强、GraphRAG 推理和成长闭环沉淀能力的 AI 面试系统。
